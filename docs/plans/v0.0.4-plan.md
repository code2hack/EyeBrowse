The actual floating-panel defect remains the #61 objective; reuse I61-T01/T02/T03 with their attributable history, rather than minting a duplicate ticket/budget. **Exact implemented behavior at `03de921`:** `LocalBrowserActivity` integrates strip motion about every 16 ms; browser input asks `BROWSER_SCROLL_TARGET` for current geometry via `evaluateJavascript`. It hit-tests the cursor's horizontal column, uses a WebView-midpoint y when the logical pointer lies outside the page, prefers a scrollable ancestor there and then a visible focused panel, and bounds distance/chaining. It returns only normalized coordinates/distance. `NativeRgInputTarget` drops late (>50ms), obsolete or ineligible results, scales vertical pixels with Android's scroll factor and dispatches native `MotionEvent.ACTION_SCROLL`/`AXIS_VSCROLL`, `SOURCE_MOUSE` with finger tool type, through `WebView.dispatchGenericMotionEvent`. There is no held DOWN/MOVE/UP touch stream and no DOM scroll assignment. Native utility lists separately use `ScrollView.scrollBy`. Android documents [ACTION_SCROLL as generic motion, separate from touch](https://developer.android.com/reference/android/view/MotionEvent#ACTION_SCROLL).

At canonical layout the midpoint fallback is screen y344 (48+592/2), or y244 with the keyboard open (48+392/2). Owner's proposed **screen** point `(current cursor x,320)` is different. Treat it as a screen-center anchor candidate, derived from actual drawable bounds and converted through current native View/global/page transforms and viewport scale; it is not CSS y320 or the page's midpoint. Preserve full-screen strip triggers. Check toolbar/keyboard/insets/visible viewport and actual panel hit; do not clamp an invalid point into a button or blindly press background content. A popup not covering that anchor, a covered ancestor or an iframe is a concrete targeting question to diagnose, not proof that touch dragging fixes it.

A narrow native touch-drag correction is within the existing native-dispatch contract and current Owner proposal; no protected-spec edit is needed **if** the following behavior is preserved. Worker chooses the smallest evidence-supported path, compares wheel versus touch on the actual failing surface, and records why it works. Touch start/move must establish scrolling without a stationary long-press dwell, accidental click/link/form activation, focus theft, text selection, draggable-content movement or duplicate pad consumption. Account for Android touch slop, minimum/maximum configured speeds and bounded strokes. Keep movement inside the qualified active surface, with correct direction and no unintended background chaining. The current Boolean reports geometry-request admission, not native consumption or movement. The selector can reject the target before wheel dispatch; changing only the event after that selector may send nothing. It does not traverse shadow roots/iframes, custom transform scrollers or other Android windows. Separate target selection from wheel-versus-touch consumer behavior. Do not automatically retry wheel with touch after an asynchronous/ambiguous result: that can duplicate an already-consumed action. If a safe press target cannot be established, stop that path and report the concrete limit; do not simulate a page click or infer safety from a later cancel.
